# 机器 ID 替换方案对比

## 背景

Kiro IDE 通过机器 ID 绑定账号配额，限制一个账号只能在特定设备上使用。要实现多设备共享账号或切换账号，需要解决机器 ID 绑定问题。

目前有两种主流方案：**本地文件修改** 和 **网络代理替换**。

## 方案一：本地文件修改（本项目采用）

### 原理

直接修改 Kiro IDE 读取机器 ID 的源头文件，让 IDE 启动时获取到指定的机器 ID。

### 实现

```
切换账号 → 修改系统机器码/IDE配置 → 重启 IDE → IDE 使用新机器 ID
```

### 涉及文件

- Windows：`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Cryptography\MachineGuid`
- macOS：`IOPlatformUUID`（通过覆盖文件变通）
- Linux：`/etc/machine-id`

### 优点

- 无需额外工具
- 实现简单直接
- 不依赖网络环境

### 缺点

- 需要管理员/root 权限
- 修改后需重启 IDE
- 会影响其他依赖机器码的软件

## 方案二：网络代理替换（K-Proxy 方案）

### 原理

通过 MITM 代理拦截 Kiro IDE 发往 AWS 的 HTTPS 请求，在请求头中替换机器 ID，本地文件不做任何修改。

### 实现

```
IDE 发送请求 → 代理拦截 → 替换请求头中的机器 ID → 转发给 AWS
```

### 核心逻辑（Lua 脚本）

```lua
-- MITM 白名单：只拦截 AWS 相关域名
local MITM_DOMAINS = {
  "amazonaws.com",
  "amazon.com",
}

-- 匹配请求头中的机器 ID 格式
-- x-amz-user-agent: KiroIDE-版本号-64位十六进制机器ID
-- user-agent: KiroIDE-版本号-64位十六进制机器ID

-- 替换规则：将末尾 64 位机器 ID 替换为目标 ID
replace_in_header("x-amz-user-agent", "[a-f0-9]{64}$", TARGET_MACHINE_ID)
replace_in_header("user-agent", "[a-f0-9]{64}$", TARGET_MACHINE_ID)
```

### 优点

- 不修改任何本地文件
- 无需重启 IDE
- 不影响其他软件
- 更隐蔽

### 缺点

- 需要安装 MITM 代理工具
- 需要信任自签名 CA 证书
- 配置相对复杂
- 依赖代理环境

## 对比总结

| 方面 | 本地文件修改 | 网络代理替换 |
|------|-------------|-------------|
| 实现层 | 文件系统 | 网络层 |
| 侵入性 | 修改系统配置 | 无文件修改 |
| 权限要求 | 管理员权限 | 普通用户 |
| 额外依赖 | 无 | MITM 代理 + CA 证书 |
| 切换速度 | 需重启 IDE | 即时生效 |
| 影响范围 | 可能影响其他软件 | 仅影响代理流量 |
| 适用场景 | 桌面应用管理 | 需要频繁切换或隐蔽场景 |

## 本项目选择

本项目采用 **方案一（本地文件修改）**，原因：

1. 作为桌面应用，可以方便地获取管理员权限
2. 用户体验更简单，无需配置代理环境
3. 与账号管理功能集成更自然
4. 切换账号时顺带重置机器 ID，流程统一
